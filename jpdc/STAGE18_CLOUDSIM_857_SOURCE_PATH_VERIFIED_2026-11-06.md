## Actual source-derived mechanism (version-specific)
1. `CloudletSchedulerAbstract.java:247–258`, `cloudletSubmitInternal`: test `canExecuteCloudlet(cle)` and, when true, place new incoming cloudlet directly in execution; otherwise enqueue waiting. No explicit waiting-queue emptiness or older-job priority gate in direct admission branch.
2. `CloudletSchedulerSpaceShared.java:95–98`: implementation of `canExecuteCloudletInternal` checks free PEs needed by **this incoming cloudlet**, not whether other cloudlets are waiting; the abstract `canExecuteCloudlet` also checks cloudlet status.
3. `CloudletSchedulerAbstract.java:477–494`, `updateProcessing`, separately calls `moveNextCloudletsFromWaitingToExecList` after processing running cloudlets.
4. `CloudletSchedulerAbstract.java:910–923` drains waiting cloudlets using `findSuitableWaitingCloudlet`. Thus the new-job admission path and waiting-list dispatch path are separate.

This **explains a mechanically possible** waiting-list bypass when a PE is free and an older cloudlet remains waiting. It is *consistent* with previously observed concrete node14 events from source-generated E45 S3 HIGH seed40: 10900 submitted first and waits; when 10901 arrives, running list empty and 10900 still waiting; new 10901 directly executes.
