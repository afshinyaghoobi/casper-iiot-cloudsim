## Prospective A2 and follow-up A3 novelty/status distinctions

- **A2 prospectively frozen**: 24 synthetic conditions, 288 actual Java jobs, both primary and independent auditors PASS. Different wait/finish classifications from explicit FIFO *model* are real measured model-to-model differences for these fixed conditions.
- **A2 hindsight service sensitivity POSTHOC**, not another independent study: 250/288 native-reported execution durations differ from requested length, worst requested FIFO wait residual 246ms and worst posthoc native-duration FIFO residual 154ms; case maxima differ by scenario and cannot be used to claim isolated causal fraction.
- **A3 exact-version wait/source and runtime origin**: `getStartWaitTime` defined as start minus Datacenter arrival; native Datacenter arrival and scheduler-submit timestamps **equal for 288/288 jobs** in fixed A2 cases. Therefore the 246ms max discrepancy is NOT a clock-origin artifact for this *specific* setup. This finding does not prove general FIFO failure or cross-runtime equivalence.
- **Prior FGCS manuscript** already includes original CASPER algorithm, queue counterfactual caveat, feedback and S3 observations. Do not recycle any into new original paper.

## Editorial judgement (not an irreversible rejection)

**Candidate contribution that can be defended in current sources:** an exact-version, explicitly bounded reproducible diagnostic showing how native event-driven queue admission/list updates, simulator-reported execution duration, and a deliberately simpler analytical FIFO reference can yield markedly different waiting/deadline classifications in predefined small synthetic cases—with controls for listener intrusion and wait-clock origin. No new algorithm, theorem, actual distributed network deployment, external workload source or proven simulator defect.

**Novelty breadth for full JPDC research article remains WEAK/UNPROVEN**, since (i) simulator and analytical cross-model validation existed, (ii) CloudSim duration inaccuracies existed, (iii) submit-time consequences existed, (iv) only one VM with CPU-only micro-workload tested here, and (v) there is no demonstrated **actual scheduling-decision change** caused by interpreting models differently. Don't increase sample size mindlessly; if pursuing JPDC, a minimal, independently defensible causal scheduling-evaluation consequence—not cosmetic grid expansion—would need explicit rationale/preregistration. Alternatively select a more suitable simulation-methods/software journal.

**Go/no-go:** CONTINUE MANUSCRIPT COMPLETION, but do NOT claim JPDC submission-ready or press submit merely because v0.5 exists. A hard author decision between appropriate publication venue and scientific contribution remains.
