**Primary technical question**: Does a SQLite, bounded-row-batch inventory faithfully preserve source-file `job_id`, `(job_id,task_index)` sets and event counts, and can a crash or replay not create a false complete-source record or duplicate source evidence? This is a software correctness test, not a new physical experiment, independent source cohort, conformal prediction or JPDC policy efficacy.

### Design and strict gates
- Original per-source GCS name, exact generation, expected size and full-gzip SHA256 are fixed. Input archived source gzip is verified **before** source is marked complete; ensure gzip EOF/trailer verified; original v2.1 exact 13 CSV columns, nonnegative timestamp and keys, codes0..8, monotonically nondecreasing file time.
- DB tables `file_inventory`, `job_presence`, `task_presence`, `event_counts` (all original job/task identifiers preserved as INTEGER, no truncation or lossy hash). File identity keyed by index, generation/hash; `job_presence` primary key (file_index,job_id), `task_presence` primary key (file_index,job_id,task_index). Ingest within transaction and commit **only after full verified input and expected source semantic counts**, fail closed on duplicate/mismatch.
- SQLite `PRAGMA cache_size=-8192`, `temp_store=FILE`, transaction atomic; event buffer max **1024 rows**; source input max 2million rows and 128MiB inflated, and original gzip <=1,502,643 bytes. DB file size cap **256MiB** for this pilot. Do not store full task event record rows permanently, only aggregates and job/task source presence.
- Resume with the **identical source SHA and generation** must be no-op: DB bytes/file counts and `file_inventory` unchanged; mismatching generation or SHA must reject. A fully failed/malformed ingestion must roll back completely; verify negative fixtures. Never count two CI runs as independent data.
