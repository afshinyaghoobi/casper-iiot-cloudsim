## Important correction to future operational assumptions
A prior SQLite ingest implementation checks `file_inventory` generation and original compressed SHA and returns `ALREADY_VERIFIED_NOOP`. These fields alone cannot detect post-ingest deletion or alteration of presence rows. This preflight adds an offline *fail-closed* SQL count / source-event total / orphan check, and synthetic negative tests clearly demonstrate that a database with `COMPLETE` file status but incomplete presence records MUST be rejected. **Do not claim the original ingest's no-op resume path was changed**: the production ingest source remains unchanged; the new preflight is a separate gate. For actual 500-file ingest, integrate per-source canonical exact-key digests or original source-backed independent reparse before promoting whole-dataset resume security. Merely testing cardinalities is not sufficient against arbitrary same-count corruption.
