## Pre-outcome protocol and implementation

New `jpdc/feedback_deadline_scheduler.py` and isolated `jpdc/independent_physical_feedback_deadline_stage37.py` source clone. 21 original nodes, unmodified strict FCFS Python physics, original workload and stochastic shock scenarios. Three fixed feedback policies:
- `NEW_CPU_FEEDBACK_ONLY`: per node positive CPU service-time prediction error 75th percentile of latest32 CPU FINISH labels (min4).
- `NEW_E2E_FEEDBACK_ONLY`: per node positive network delay residual 90th percentile of last32 **E2E DELIVERED** outcomes (min8), reusing prior `NetworkResidualRisk` observed E2E feedback.
- `NEW_CPU_E2E_FEEDBACK`: sum the two penalties. None guaranteed, conformal or certified.
At task arrival, candidate nominal latency cannot exceed original PRED_GREEDY minimum by more than **2ms for MISSION** or **5ms for HIGH/NORMAL**. Prefer corrected-prediction-feasible candidates at deadline then smallest corrected predicted latency, with node-index tie break. No oracle future CPU/network or hidden affected-node mask; no route changes after dispatch, no probes. New policies are unverified heuristic; small budgets are engineering assumptions not validated constants. Original FGCS E42 git blob SHA `34256ca7bff46f911cf20e8b94278fbd09175746`, E4.6 unchanged.
